# ADR 0003: 候选＝知识注入通道；命名校准合一（term/naming），表述理顺归润色

日期：2026-09-16 收敛、2026-09-17 用户定稿正文｜状态：已实施

## 决策

候选系统只做一件事：**把你说话里说不清的点，校准成对的名字**。

- 一份任务书「命名校准」（替代原「候选生成」）。权威定义（用户定稿）：**说话里总有一些说不清的点：可能是一个东西、一个东西里的某个部分、几样东西之间的关系等等——你只能绕着描述。AI 把这些点逐个找出来，不管卡不卡词都做校准**——业界已有叫法的给本名＋一句外行能懂的大白话解释（回指原话，认出指的就是它）；还没有公认名字、要新造的按领域惯例起名＋理由，尽量沿用本名作词根；一个点只出一个名字，优先挑最影响理解的点（总量上限照旧）。
- **动作与卡词无关**（2026-09-17 裁决）：说不清的点在说话里客观存在，不等价于说话人卡住；出不出候选由「有没有说不清的点」定，不由「是否卡词」定。
- **现造词一并校准**（2026-09-17 裁决）：说话人绕着描述时会现造很多词——生造的、说偏的、碰巧说准的都要过一遍校准（说准的确认＋解释，让说话人放心；说偏的给本名）。
- **纯展示提示，不可交互**（2026-09-17 裁决，同日扩展到推荐）：候选 chip 与推荐行都不点选、无 [存]、口头命令「用候选N/用常用语N」全部废除。提示的消费者是人不是待融队列——推荐展示的就是常用语触发词，用户看中哪个**直接读触发词**，命中机制自然接住；用户看到候选提示后自己说出来，由润色流自然吸收。不替用户贴词。选择子系统（口头命令解析、toggle 点选、选中态、选中撤销臂）整体移除；历史 `ghostwriter_selections` 字段为旧记录只读保留。
- 输出契约 kind 从 `term|phrase|naming` 改为 `term|naming`；phrase（顺句）从候选移除，归润色职责（形式自动处理，无需用户选）。
- 分界原则：**润色管形式（自动、每段、无需选），候选管知识注入（用户没说、但这句话需要的东西，必须用户点头）**。

## 为什么

1. phrase 与指令化润色重叠：顺句是形式问题，润色流已在做；候选里再放一份＝重复＋噪音。
2. term 与 naming 同产物（名字）同链条（认出行话→用行话给新造物起名）；拆两份任务书会对同一个点给出互不相干的双份名字，「先认后造」的决策规则必须写在一份正文里才连贯。
3. term chip 必须配白话注释（识别优于回忆，NN/g #6）：用户说不出术语是回忆失败，看到「术语＋就是你说的那个X」能认出来——注释同时拦截 AI 认错所指（"讲成另外的东西"在贴出前被发现）。
4. naming 要配理由：命名是 Agent 时代的性能特征，坏名字固化进实现、事后改名触及每一处调用点（Symvanta《Should You Rename Your Code for AI Agents》；微软 HAX Toolkit Pattern 10A「行动前消歧」：给选项优于追问、最可能的排前）。

## 替代对照

- 拆三份任务书（术语补全/表述理顺/命名校准）：否——phrase 与润色重叠；term/naming 链条被拆断。
- 只重写「候选生成」一份正文不拆不并：否——三判据挤一份正文成大杂烩，调优互相牵制（本方案即其修正态）。
- 反问澄清（AI 提问）：否——打断说话流；任务型语音对话研究显示给选项优于多回合追问。

## 失效条件与盲区

- 若「卡在半句不知道下半句怎么讲」成为高频痛点，那是**续写**功能（另立），不是恢复 phrase。
- 多点场景的归属呈现靠注释回指（「就是你说的那个X」）；若未来证明不够，再考虑按所指分组展示（未做）。
- 白话注释在浮框上的展示形态（hover/小字）实施时定。

## 追加裁决（2026-09-17）：沉淀链路退役，提取改道管理页

- **常用语提醒整体删除**：任务书、浮框提醒条（存/✕）、assist 输出契约的 sediment 槽。纯展示原则推到底后，提醒条是浮框仅剩的按钮面，且其价值（提醒你存说法）被手动提取覆盖。
- **重复档（recurrence store）随葬**：它存在的唯一理由是供提醒比对重复；提醒没了，说话中自动提取＋计数＋节流全成死设施，一并移除。
- **提取改道为管理页手动批量**：常用语管理页新增「从语音记录提取」——多选最近 3 天语音记录（显示相对时间）→ LLM 批量出候选（说法＋建议触发词＋例句）→ 候选就地编辑 → 多选保存（表述类·启用）。**先编辑后入库**；重复触发词沿用既有拒绝逻辑就地标错。任务书剩四份（指令化润色/命名校准/常用语推荐/提取常用语），提取正文改为批量语义。
- 为什么不用「待确认状态＋自动入库」：中途推演过自动提取进待确认列表的方案，被否——全自动必然混入垃圾，而编辑确认链路（先编辑后转正）与手动提取天然重合，省掉整套待确认状态机与去重负担。
